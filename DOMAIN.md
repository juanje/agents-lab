# Domain

What the words mean here, how the pieces fit together, and how the tools behave on the pinned versions. When a pinned version differs, check the behaviour before relying on it, and update this file.

## Terms

| Term | Means | Not to be confused with |
|:--|:--|:--|
| Agent | One participant in a world: a model, the harness that runs it (a Pi session for the whole run) and the memory it keeps. | The model alone. Two agents can use the same model. |
| Tool | An agent's only interface with the world: a sensor or an effector, declared by the scenario with its description, arguments, duration, effort and failure reasons. | A function of the engine. Tools are what the agent's session offers. |
| Sensor | A tool that returns part of the world as seen from where the agent is, when its duration ends. It changes nothing. | An observation handed to the agent. Nothing is handed; the agent senses. |
| Effector | A tool that changes the world through the arbiter, when its duration ends. One under way in the world, such as crossing a passage, can also declare a start, applied through the arbiter as its call starts, once its duration is taken (FR-SPACE-03). | Text the agent writes, which acts on nothing. |
| Reflection | The text an agent writes in a model turn. It is recorded and reaches no one. | An action. |
| Stimulus | A message delivered into an agent's session through a declared channel, with its source (another agent or a mechanism of the world). | A tool result, which the agent asked for. |
| Channel | A declared path by which stimuli reach agents, naming their source (for example the agent's rhythm). | A tool. |
| Activation | A stretch in which an agent is awake: it starts with a stimulus from its rhythm and ends when a model turn makes no tool call. | A turn. Activations of different agents overlap and run at different paces. |
| Model turn | One call to the agent's model within an activation, giving text, tool calls or both. | An activation, which can hold many model turns. |
| Rhythm | The distribution an agent draws its waiting interval from between activations. | A turn. Rhythms are independent per agent. |
| Duration | The time a tool call takes before its result or effect. It can depend on the arguments and the state, such as distance. | Latency, which is the model's time. |
| Effort | The energy a tool call spends when it starts. | Duration. |
| Energy | An agent's capacity to act, up to a maximum; spent by effort and recovered by a process. The agent knows it only through a declared sensor or result. | A metric. |
| Process | A change the world applies on its own at an interval, through the arbiter (for example energy recovering). | An agent's action. |
| Component | A part of the world besides the agents that follows its own life cycle and calls no model (a porter on his rounds), declared by the scenario from its configuration as part of the world or an external perturbation (FR-PROCESS-01). Its cycle chooses each step (a wait, an action, or its end) from the world's state, its own random sequence, its last action's outcome and the time since the run started. | An agent, which has a model and acts only through tools; a process, which has no cycle or goals. |
| Adapter | The code that runs an agent's Pi session: its system prompt, tools, stimuli and model. | The agent. The adapter is how the engine talks to it. |
| World | The state of a scenario (entities, positions, quantities, energy) plus its arbiter. | The scenario, which also declares tools, channels and metrics. |
| Arbiter | The part of the world that applies one effect at a time against the current state. | A scheduler. The arbiter never decides who acts next. |
| Version | A counter of applied effects in a world. | A run id or a code version. |
| Scenario | A TypeScript module in `src/scenarios/` (its agents, initial state, tools, channels, metrics, and a system prompt and a rhythm for each agent, and optionally the channels of its first stimuli; agents, channels, prompts, first stimuli and rhythms from the configuration; and, for the inventory, text from the configuration that describes how each tool's duration and each agent's rhythm are computed, and, for a scenario that seeds situations, the ids of the situations the configuration chooses; and optionally its components, from the configuration) plus its base configuration, reusable by several experiments. | An experiment, which runs a scenario under several conditions. |
| Test scenario | A small scenario under `tests/fixtures/`, written only to test the engine. | A library scenario in `src/scenarios/`, which experiments use. |
| Condition | A named change over a scenario's base configuration, written directly or produced by combining factor levels. | A run or a replica. |
| Experiment | A file in the experiment language (TOML) in the experiments repository: scenario, factors and conditions, models, thinking level, compaction, replicas, seeds, prediction and materials. | A hypothesis, which the experiment states and tests. |
| Replica | One run of a condition with one model and one seed. | A fork, which continues a saved state. |
| Run | One execution of one replica; produces one log file. | An experiment, which is many runs. |
| Outcome | The single recorded result of a tool call: `success`, an engine failure (`invalid_arguments`, `no_energy`, `cut_off`, `cell_full`) or a failure reason of the world the scenario declares (for example `slot_taken`). It never says what the agent knew: that is recorded beside it as what the agent last sensed of its target (`free`, `held`, `outside`, `not_sensed`). A model turn ends with `success`, `model_error`, `timeout` or `cut_off` (the run's time limit passed during it); a script that runs out records `script_exhausted`, recognised by the faux provider's error text "No more faux responses queued" (`SCRIPT_EXHAUSTED_MESSAGE`); a Pi upgrade that changes it makes FR-ADAPTER-01's scenario fail. | A metric. |
| Changes since sensing | For an effector call, the number of effects other agents and components applied between the agent's last sensor call and the moment its effect was applied, recorded with the agent or component behind each of them, by name, in the order they were applied (`changesSinceSensingBy`); both are null when the agent had not sensed. | Latency. |
| Stale action | An effector call whose changes since sensing is above zero. | A failed call. A stale action can still succeed. |
| Target as sensed | What an agent last sensed of an effector's target before the call: `free`, `held`, `outside` (its last sensing showed the target is no place it can go) or `not_sensed`. Recorded beside the outcome. An effector's `readTarget` gets the agent's last sensing and `lastBy`, its last sensing by each sensor, by name, whatever it sensed after it: the workplace reads its targets in the worker's last look, so a later `read` or `examine` does not replace that look. `not_sensed` without reading when the agent has sensed nothing. | The outcome, which only the world decides. |
| Latency | Time from a model turn's start to its answer. | Wait for a slot, which comes before the call. |
| Wait for a slot | Time a model turn waited because the parallelism limit was reached. | Latency. |
| Parallelism limit | The maximum number of model calls running at once. | The number of agents. |
| Inventory | The generated list of everything an agent meets in a scenario and condition. | The log. |

## How the pieces fit

- **Each agent is a Pi session** that lasts the run, driven by an async loop on Node's event loop: wait the rhythm, wake with a stimulus, run model turns and tool calls until a turn makes no call, then wait again.
- **Every tool call goes through the world:** a sensor reads it when its duration ends, from the state, the calling agent, the call's arguments and the time since the run started (the run's `RunClock`, started when the agents can start, the moment the time limit counts from; the workplace turns it into its clocks' time, FR-WORKPLACE-05, and the read of its book turns each entry's `atMs` into the time the clocks showed then, as the entry's moment less the run's start, `performance.now()` less that time); an effector's effect is checked and applied by the arbiter when its duration ends, and its action gets the call with `atMs`, the moment it is checked and applied, by `performance.now()` (a `LandingCall`), so a world can keep when something was written. An effector's start, when it declares one, is applied as the call starts and counts among other agents' changes since sensing; a start the world refuses stops the run, as a tool that throws does. A start that declares `appliesTo` is applied only to the calls it applies to; a call it does not apply to (the workplace's `go` to a place out of reach) starts nothing and writes no `effector_start` line, and its action alone gives its outcome. An effector with no action (the workplace's `wait`) changes nothing: its call goes through no arbiter and succeeds. An effector may refuse a call's arguments from the state as it starts (`refuses`), for a limit its schema cannot give, such as one the configuration sets; the call is `invalid_arguments`, with `invalid_arguments: <its reason>` as its text, applies nothing and takes no time. An effector may declare an early end (`endsEarly`, FR-WORKPLACE-07): once its start is applied, its call watches the world's changes (`World.watch`, each with the state before and after it) and its agent's stimuli (`Stimuli.watch`, which takes none of them from the session); the first its conditions accept ends the call there, its effect is checked and applied then, and its outcome is the early end's when the effect applies, or the failure's reason when it does not. The arbiter is the only writer of the world's state.
- **Stimuli** from channels enter the session at the agent's next model turn, or when it wakes. A scenario may give each agent first stimuli (`firstStimuli`, channel names from the configuration, each declared, or loading refuses them): the agent receives them once, as it first wakes, right after the rhythm's and before any that arrived while it rested (the workplace's person's first message, FR-WORKPLACE-03).
- **Processes** change the world on their own schedule, through the arbiter.
- **Components** run alongside the agents from the moment the agents can start (`runComponent`), each on a random sequence derived from the replica's seed and `cycle of <name>`, so adding one leaves the others' sequences as they were. A component's action takes its duration, then is checked and applied through the arbiter as an effector's is (`applyCounted`, shared with effectors), and counts by the component's name among the changes since sensing; its cycle gets the outcome, and the time since the run started, before it chooses again. An action may have a start, applied through the arbiter as it starts and counted by the component's name, as an effector's (the porter's walk leaves as each crossing starts); a start the world refuses stops the run, naming the component and its action. The start writes no line of its own: the action's `component_action` line covers it. The run ends once every agent and every component has ended, or at its time limit, which cuts off an action still running: it applies nothing and is recorded `cut_off`. A run may have components and no agents. A run whose agents and components do not all have different names is refused before its log opens, naming the name taken twice.
- **The recorder writes a line per event.** The inventory and the run's setup go first.
  - A run of an experiment writes `run_setup` first (FR-RECORD-02): its run id, experiment, `scenario` (its name in the library, which the judge asks what it declares), condition and resolved configuration, replica, seed, model, the code's commit and whether its working tree had uncommitted changes (git, run in the engine's own directory; a run fails before it starts when git cannot tell), the condition's inventory as data, `compaction` (the experiment's setting, FR-ADAPTER-03), `parallelRuns` (the experiment's `parallel_runs`, FR-RUN-06), and `sampling`. Each session gets the experiment file's `thinking_level` (FR-EXPERIMENT-05), read back from each opened session into `sampling.thinkingLevels`; the engine sends no other sampling parameter, so every other one is the provider's default. Pi 1.5.0 would clamp a level a model cannot use to another without saying so (and default to "medium" when given none), so `runExperiment` checks the level against Pi's `getSupportedThinkingLevels` for every model before the first run and refuses it, naming the model and the level; a model without reasoning can use only "off". So the line is written once the sessions are open, before `onStart` is called; when a session fails to open, it is written with `sampling: null` before `run_stopped`. A direct `run()` without `setup`, as tests make, writes none.
  - Each run opens a new `<run id>.jsonl` in the log directory it is given, created exclusively (it refuses a file that is already there), and writes each line at once, synchronously.
  - Lines: `run_setup`, `activation`, `stimulus` (as it is delivered: a channel's when `Stimuli.deliver` is called, the rhythm's and the agent's first stimuli as the agent wakes), `model_turn` (with `reasoning`, the answer's thinking blocks' text joined, only when the provider returned any; a redacted block is recorded as Pi gives its text), `effector_start` (as an effector's start is applied: the agent, the tool, `atMs`, the moment its call started, and `change`, as the effector's `describe` gives it from the state before), `tool_call`, `component_action` (as a component's action ends: the component, the action's name, when it started and ended, and its outcome), `compaction` (as each compaction Pi starts on an agent's context ends: the agent, `reason` `threshold` or `overflow`, `outcome`, when it started and ended, and the `tokens` and `cost` of its summary calls, summed when Pi made two; one with the outcome `success` also gives `contextTokensBefore` and `contextTokensAfter` as Pi estimates them and the `summary` the context holds from then on, and one that did not finish, `model_error`, `timeout` or `cut_off`, gives neither), `metric_sample` and `run_stopped`. Every time in them is by `performance.now()`.
  - The first error that stops a run writes `run_stopped` with its message at once and aborts the run as its time limit does; nothing is written after it. A tool that throws, or a session that fails to open, stops the run: the scenario's defect, not the agent's behaviour, so the call that threw has no `tool_call` line.
- **Metrics read the state and the tool calls so far** (every agent's `ToolCall` records, in the order they ended; a call still under way is not among them) at the start (once every session is open, when the time limit starts), every `metric_interval_ms` of the experiment file (each sample at least that long after the previous one, by `performance.now()`), and at the end, once every agent has stopped. Each `metric_sample` line gives `atMs`, the world's `version` and each metric's value: a number, `null`, or an object of values by name (an agent's, or a situation's id). The workplace's metrics (FR-WORKPLACE-04) give one value per chosen situation, leaving out a situation with no value yet. A situation's things (`situations[id].things`) are those its text brings, then those its predicates name, which can be things of the world; all count for `sensed_at_ms` and `acted_at_ms`. A thing's location is where it directly is: `held` (the worker's hands), `person:<id>`, the container it is in, or its place, so a thing inside a box in the store is in the box, not in the store. The world keeps each move of a thing (`moves`: from, to and the moment it landed, by `take`, `put` and `give`), and `settled_at_ms` replays them to find when a situation's predicates last changed. `sensed_at_ms` and `acted_at_ms` are the end of the worker's call; `exploration` counts its calls after the sensing one that started no later than the settling move; `entries_after` and `notes_after` count what was written at or after `sensed_at_ms`, and give no value before it. A thing in no place (one that has not arrived, FR-WORKPLACE-05) has no location: no `where` holds for it, every `not_where` does, and it is given to no one; its arrival is not a move.
- **The depot's day** (FR-WORKPLACE-05): the world's `[day] start` (midnight when it has none) and the configuration's `time_scale` (1 by default) set the clocks (`state.clock`); only `check_time` gives the worker the time. Every clock time is `"HH:MM"`, turned into run time as `(seconds − start) / time_scale` seconds. The porter (`state.porter`) and each visitor (`state.visitors`) are components and people of the space (`state.people`), in no place until they appear and after they leave; a porter's or visitor's id that a thing or a person already has is refused, as are a thing that arrives at no round of the porter's or in a world with no porter, and a porter whose `enters` and `drops_in` no passages join. Each round's things are the world's things marked `arrives` and the top-level things of the situations `arrivals` lists for it (an arriving situation is placed in `drops_in`, not by the seed); the porter appears in `enters` holding them, walks the shortest way (passages declared first win a tie) with `ms_per_length`, puts them down in `drops_in` with `put_ms`, walks back and leaves; appearing and leaving take no time. A visitor's arrival is drawn from their own sequence between the two times of `arrives_between`; they appear in `enters` and put down at once the top-level situation things marked `brought_by` them, notice what they hold each depot second, and leave once they hold all of `comes_for` or after `waits_minutes`. The worker's `wait minutes` (FR-WORKPLACE-07) lasts that many depot minutes, from 1 to the configuration's `wait_max_minutes` (60 in the base configuration; any other number is refused as `invalid_arguments`), changes nothing, and ends early as `interrupted` when a person (one of `state.people`: a person, the porter or a visitor) is in the worker's place after a change and was not before it, from a passage or appearing there, or when any stimulus reaches the worker; that stimulus still waits for the worker's next model turn.
- **The runner** expands an experiment into runs (each condition with each model, for each replica, replica r's seed derived from the base seed and r) and starts them in that order, each next one as soon as one ends, so no more than the file's `parallel_runs` (1 by default) are in progress at once (FR-RUN-06). Each run has its own world, sessions, parallelism limit and log; its line in the experiment's `index.jsonl` is written as it ends, so the index lists runs in the order they ended. The runs in progress share one stop signal, whose reason is the error each stops on: the first run that stops on an error aborts it with "the experiment stopped: <that run> stopped", and an interruption with "the run was interrupted" (`run()` takes an `interruption` signal's reason, when it is an `Error` other than Node's own `AbortError`, as the error it stops on). No run starts after the signal; the experiment fails with the first run's error once every run in progress has ended. The observer (`ExperimentObserver`, which `lab run`'s progress implements) is told each line and each end by the run's number; while several runs are in progress, each progress line gives each of them, joined by "; ". `readExperiment` first expands the file's factors into conditions (FR-EXPERIMENT-02): `baseline` (unless `baseline = false`), then every combination of levels, named `factor=level,…` in the file's order with the first factor's levels changing slowest, then the file's own `[conditions.*]`; a name given twice is refused. A combination's change is its levels' changes merged, and two levels that set the same key (a material's reference counts as one value) are refused. `[common]` reaches every condition as `Condition.common`, which `loadScenario` applies before the condition's own change; a common material whose key the condition sets again is not listed. Only a combination has `levels`, and its setup line and index line give them; any other condition's lines have no `levels` field. `lab run` resolves the scenario from the library and the models by name before any run.
- **The inventory** is generated from the scenario as each condition configures it, plus the experiment's models and limits. It is data (`inventory()`, one entry per condition); `lab inventory` prints it as Markdown (`inventoryMarkdown()`), one `## Condition` section each, without loading any model or writing anything. What the engine does not provide yet (energy, environment processes, tool efforts) is listed as "none", and every sensor and channel as instant. An effector's outcomes are listed from the texts it declares, since effectors do not declare their failure reasons yet; each condition also lists the outcomes the engine itself gives any call (`invalid_arguments`, `unknown_tool`, `cut_off`) with what the agent receives for each. Each agent's first stimuli are given beside its system prompt, with their channel and source. A scenario that seeds situations (the workplace, FR-WORKPLACE-01) gets a `situations` part listing the chosen ones by id only, never their things or reserved keys; a scenario without situations gets none. A scenario that declares a clock (`Scenario.clock`, the workplace, FR-WORKPLACE-05) gets a `clock` part with the time it shows when the run starts and its time scale ("### Clock"); a scenario without one gets none. Each condition gives the experiment's compaction ("### Compaction"): off, or on with `trigger_at` and `keep_recent_tokens` and Pi's texts for writing a summary, the system prompt and the three sets of instructions (`summaryInstructions`). A scenario with components gets a `components` part listing each one the condition declares, with its kind (part of the world or external perturbation) and its cycle as the scenario describes it, or "none"; a scenario without components gets none.
- **The summary across replicas** (`summarizeRuns`, `src/analysis/replicas.ts`; FR-RUN-02) reads only a runs directory's `index.jsonl` and the run logs it lists; `lab summarize <runs-dir>` finds the directory from where it runs and prints it as a Markdown table (`summaryMarkdown`), or with `--json` as the same rows in JSON. A row is a condition and model (in the order the index first lists them) and a metric, or, for a metric whose value is a record, one agent or situation of it (the row's `key`). Every condition and model gets a row for every metric and key any completed run gives, so one whose runs all stopped still shows its counts. Each row gives its runs completed and stopped, the values of its completed runs' last `metric_sample`, in replica order, with the replica each came from, the number of nulls (a metric's own `null` counts on its row without a key), and the minimum, quartiles and maximum by linear interpolation, `null` (a dash in Markdown) without values. A stopped run gives no values, and a completed run whose log has no sample gives none either. A directory without an index is refused, named as it was given.
- **The reserved judge** (`judgeRuns`, `src/analysis/judge.ts`; FR-ANALYSIS-02): `lab judge <runs-dir> <judge.toml>`, both found from where it runs. The judge file (`readJudgeFile`) gives `model`, `thinking_level`, `instructions`, a material, and `timeout_ms` for each call, and, optionally, `[questions]` with `says` and `reveals`, each a text or a material: the wording that ends a question asking whether a text says, or reveals, its statement (a `questions` that is not a table, or a value that is neither, is refused); it sits beside the experiment file, so its own material and each run's setup-line materials are read relative to its directory. For each completed run (stopped runs are not judged), the judge reads the setup line and the `tool_call` lines, puts the text of each held-out material in place of its reference (refusing, by its path, a file that is missing or whose hash differs from the recorded one), and asks the run's scenario, by its name in the library, what can be judged (`Scenario.judged`, giving `Judgeable`s: situation, key, statement, whether a text must say or reveal it, and the texts with when each was written). Every run is read, and every material checked, before the judge's model is called; a thinking level the model cannot use is refused then too (`assertThinkingLevel`, the rule `lab run` uses). The workplace gives, for each chosen situation in order, its `said` with the worker's successful `note` texts, `record` entries or both (`channel` `note`, `book`, `either`), then its `not_said` with both, since a note or an entry can reveal it; a text's moment is its call's `endedAtMs`. A statement with texts is one question (`askOnce`): the instructions as the system prompt, a message of the statement, the numbered texts and the wording of what it asks (by default "Does one of the texts say/reveal what the statement states?"), and the one tool `verdict` (`verdict` yes or no, `quoted`, `reason`). Each question is a line of a new `judgements/<uuid>.jsonl` under the runs directory: `runId`, `situation`, `key`, `outcome`, `verdict`, `quoted`, `reason`, `quoted_found` (whether the quoted words appear, as written, in one of the texts; null when nothing was quoted), `model` (the judge file's name), `thinkingLevel`, `instructionsHash`, `questionHash` (the SHA-256 of the wording of what it asks, a material's being its file's hash; a statement without texts gives it too), `tokens`, `cost`. A call that errs (`model_error`, with the provider's `message`), runs past `timeout_ms` (`timeout`), or ends without exactly one valid `verdict` call (`invalid_verdict`) gives a line with that outcome, null `verdict`, `quoted`, `reason` and `quoted_found`, and the tokens and cost Pi reported, and the judge goes on. A statement without texts is `success`, "no", with no call: `quoted` and `quoted_found` null, `reason` "no text on the channel", `tokens` and `cost` null.

## How the tools behave

### Pi SDK (1.5.0: `@earendil-works/pi-coding-agent`, `@earendil-works/pi-ai`)
- **Opening a session:** `createAgentSession` opens one.
  - `SessionManager.inMemory()` keeps it out of the disk.
  - A `ResourceLoader` whose `getSystemPrompt` gives our prompt replaces Pi's preamble, but Pi still appends sections of its own, such as `<cwd>`. Only a forced prompt is sent as it is: Pi forces one by replacing the system message in `session.agent.transformContext`, and the adapter does the same.
  - `tools` is an allowlist that filters custom tools too: `tools: []` leaves the session with no tools at all. Name every custom tool in it; the built-in tools stay out.
  - `session.agent.streamFunction` is the one call per model turn; wrapping it gives the place to wait for a slot, time the turn and abort it through its signal. An aborted answer ends the agent's run without running its tool calls.
  - The offered tools are kept in the session as a system message with empty text and `toolsAdded`; the system prompt itself is not a session message, and the forced prompt is sent in its place.
  - **Messages into a session:** `sendCustomMessage` keeps `customType` and `details` in the session, but the model receives only its `content`, as a user message; the adapter writes a stimulus as `<source>: <stimulus>`.
    - With `triggerTurn: true` it starts a run and resolves when the run ends; messages sent before with `deliverAs: "nextTurn"` go right after it, in the order sent (`AgentSession._prepareRun`).
    - Pi's steering (`steer`, or a custom message sent while the agent streams) is checked again after a turn without tool calls, and a steered message then makes another turn (`agent-loop.js`): it would extend an activation. The adapter keeps stimuli in its own queue and adds them in `session.agent.prepareNextTurnWithContext`, which Pi calls only before a turn that goes on the same activation.
    - A model call made with a signal that is already aborted never reaches the provider: Pi ends it as aborted first (seen on 1.5.0 with the faux provider, whose response factory was never called). A turn that waited for a slot past the run's time limit relies on it, and FR-CLOCK-02's scenario fails if a Pi upgrade changes it.
    - `session.agent.finishTurn` is called after every turn that was not aborted or an error, once its tool calls are done; returning `{ action: "end" }` ends the activation before Pi prepares another turn. The adapter ends it there once the run's time limit has passed (FR-CLOCK-02).
  - Pi retries a provider error by default, with backoff (about 2 s), and the retry takes the next scripted answer; `SettingsManager.inMemory({ retry: { enabled: false } })` turns it off.
  - oid's `src/pi-executor.ts` uses this pattern.
- **Compaction** (`compaction.js`, `AgentSession._checkCompaction`, `_runAutoCompaction`):
  - Settings `enabled`, `reserveTokens` and `keepRecentTokens`, given through `SettingsManager.inMemory({ compaction })`; Pi's default is on, with a reserve of 16384 tokens. `shouldCompact` starts one when the context is above the window minus the reserve, so `piCompactionSettings` makes the reserve the part of each model's window above `trigger_at`.
  - Pi checks before every model turn after the first of an activation (`prepareNextTurnWithContext`), so a long activation compacts in the middle; it checks after an activation and before the next one too. A compaction emits `compaction_start` (reason `threshold`, `overflow` or `manual`) and `compaction_end`, whose `result` gives `summary`, `tokensBefore`, `estimatedTokensAfter` and the summary calls' `usage`; one that fails or is aborted ends with no result, and the context stays as it was. A summary call that comes back aborted is not a failure to Pi: `getSummarizationFailure` fails only an error or a length stop, so an aborted call would leave an empty summary in the context unless Pi's own compaction is aborted too (`session.abortCompaction()`, whose signal the call carries). Pi also starts a compaction as an activation ends, after the run's end too; `session.setAutoCompactionEnabled(false)` stops that.
  - The summary is written through `session.agent.streamFunction`, the call the adapter wraps for model turns; the adapter tells it by its system prompt (`isSummaryRequest`), runs it under the same limits as a model turn (`limitedCall`: a slot under the parallelism limit, the model turn timeout and the run's end), and records it as no model turn. A call stopped by the timeout or the run's end aborts the whole compaction, recorded `timeout` or `cut_off`; a provider error fails it, recorded `model_error`. Once the run has ended, the session's auto-compaction is turned off, so no compaction starts after the end, as no model turn does.
  - When the kept part starts inside a turn (a long activation is one turn of Pi's), Pi summarizes that turn's start with its split-turn instructions and composes the summary as `<history>\n\n---\n\n**Turn Context (split turn):**\n\n<text>`, the history being "No prior history." when nothing came before; with history to summarize too it makes two calls and sums their usage.
  - The prompts are not exported. `summaryInstructions` reads them at load from the requests Pi's exported `generateSummaryWithUsage` and `compact` make, answered by a stream that calls no model.
  - The faux provider's `contextWindow` is 128000 unless a model definition gives one (`ScriptedModel`'s `contextWindow`); it estimates a prompt's tokens as its characters over 4 and counts them as cache reads and writes when the call has a session id.
- **One question** (`askOnce`, the judge's): the same isolated session as an agent's (`isolatedSession`), whose one tool does nothing; `finishTurn` returns "end" after the first turn, so the tool's result never reaches the model and the question is one model call. Its `streamFunction` adds a timeout's signal to the call's; an aborted call ends with `timeout`, an error answer with `model_error`, and either gives no calls. The calls are read from the assistant message's `toolCall` blocks, as the model made them, before Pi validates or coerces them.
- **Events:** `session.subscribe` streams messages, thinking, tool calls with their results, and the agent's lifecycle. Assistant messages carry `responseModel` (the model that actually answered) and usage, with `cost.totalFromProvider` telling billed totals from catalog estimates.
- **Tool events and timing:** Pi emits `tool_execution_start` before it validates a call, and with parallel execution (its default) it emits the start of every call in a batch before running any of them (`agent-loop.js`). The adapter sets `session.agent.toolExecution = "sequential"`, so a turn's calls run one after another. A call's start and end are measured inside the tool's `execute`; Pi's events time only the calls it answers without running them.
- **Calls Pi answers without running the tool** are recognised by why (`unrunOutcome`): a tool the session does not offer is `unknown_tool`; `invalid_arguments` when `validateToolArguments` (exported by `@earendil-works/pi-ai`, the function Pi validates with) rejects the raw arguments with exactly Pi's answer; `cut_off` once the run has ended. Any other reason stops the run. A call that reaches `execute` after the run has ended is left unrun: `cut_off`, with no target read.
- **A tool that throws** is answered by Pi with an error result, as if the call had failed, and the agent goes on (`executePreparedToolCall`, `agent-loop.js`). The adapter catches the error inside `execute` first and stops the run with it.
- **Tool arguments are coerced** by `@earendil-works/pi-schema` before a tool sees them (numeric strings become numbers, a single value becomes an array). Record the raw tool call from the events, not only the coerced arguments, or malformed answers disappear from the data.
- **Tests:** `fauxProvider()` from `@earendil-works/pi-ai` gives scripted answers (`fauxText`, `fauxToolCall`), with an optional tokens-per-second rate. oid's `features/support/scripted-model.ts` is an example.
  - A response factory receives the normalized transcript: the tools offered with `Models.complete(model, { messages, tools })` arrive as `toolsAdded` on a leading system message, and `getCurrentTools(messages)` gives them back.
  - `fauxAssistantMessage` keeps `stopReason: "stop"` even when its content holds tool calls; read the content, not the stop reason, to tell whether a turn called a tool.
  - A response factory also receives the call's options: `sessionId` names the Pi session the turn came from, and `signal` its abort signal. The provider waits for the factory before it checks the signal, so a factory that ignores it holds the call (and its model slot) for its whole delay; the scripted model stops waiting on abort, and the provider then answers with `stopReason: "aborted"` and empty content.
  - Pi's model runtime keeps one provider per id: two faux providers with the default id serve each other's calls, so each scripted model has its own.
  - Past its script, the faux provider answers with `stopReason: "error"`, `errorMessage` "No more faux responses queued" and empty content, so a turn past the script makes no tool call.
- **Authentication:** the lab's login lives in `~/.agents-lab/pi/auth.json` (D-08) and serves every session in the process. The person creates it once with `PI_CODING_AGENT_DIR=~/.agents-lab/pi pi` and `/login`. On this machine `ANTHROPIC_API_KEY` is set to an invalid key; remove it from the environment so Pi uses the login.
- **Isolation:** without an explicit `agentDir`, the SDK falls back to `~/.pi/agent/` and reads the person's settings and model definitions; `ModelRuntime.create` likewise defaults its models file there (seen in Buddy, NFR-SEC-19), and writes `auth.json` and `models-store.json` into its directory when they are missing. Pass the lab's directory everywhere a path is taken, use `SettingsManager.inMemory`, and give `createAgentSession` a resource loader that returns no extensions, skills, prompts, themes or context files (oid's `resourcesFor`).
- **Concurrency:** two processes making model calls with the same login stalled every call (observed with the CLI on 1.4.0; 1.5.0 changed the auth lock). Run one experiment process at a time (FR-RUN-03).
- **Retries:** Pi's own retries of a whole model turn are off (they consumed the next activation's scripted answer). The provider client's retries inside one call stay on: a call that still fails ends as `model_error`, and one that succeeds includes their time in its latency, so latency is not pure reasoning time.
- **Models:** the lab's login is OpenAI's. The default model for experiments is `openai/gpt-6-luna`, used in oid; it answered a short prompt through the lab's login in about 3.7 s. Anthropic's models are not used: the SDK with a subscription login gave billing and quota errors before (my-ab rule 21).
- **Not used yet:** `@earendil-works/pi-agent-core`, a lower-level stateful agent, if the coding agent's session adds behaviour we do not want; and `@earendil-works/pi-durable`, experimental persistence and resumption.

### Random sequences
- Each purpose's sequence comes from `Random.derive(seed, purpose)`: a 32-bit hash of the seed and the purpose's name starts a mulberry32 generator, whose state is a counter. Two purposes could in principle start within a few draws of each other and share part of a sequence; the chance is negligible for a few agents and short runs, but grows with many agents and long runs. If an experiment needs many of both, move to a generator with a larger state.

### Node
- A timer can fire before `performance.now()` has moved its full delay (6.66 ms seen for a 7 ms timer, Node 26). Code that must wait at least a delay, as measured, waits again for what is left (`waitAtLeast` in `src/engine/clock.ts`).
- An aborted session must also free its parallelism slot; otherwise later decisions wait for a call that will never end.

## Testing agents-lab itself

- **Unit and acceptance tests use Pi's faux provider** (FR-ADAPTER-01), with delays that make overlapping decisions happen deterministically.
- **Engine tests run test scenarios from `tests/fixtures/`,** such as a small grid where two agents reach for the same cell. A library scenario's tests live with it.
- **A real model runs only in the smoke test, outside the gate.**
- **The E13 prototype** in `~/git/mesa-sandbox/schelling_async.py` shows the agent loops, the window and the collision outcomes working. It is a reference for behaviour, not code to copy.
